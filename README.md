# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone project for the AI/ML Certification Program (E&ICT Academy, IIT Roorkee).

The repo answers three questions for the regional ops team using a synthetic shipment dataset:

1. How many hours will a parcel really take? (regression, Part B)
2. Will it miss its promise? (classifier + alert threshold, Part C)
3. Which hubs need which playbook? (hub segments, Part D)

Everything is plain pandas / NumPy / scikit-learn / joblib and runs offline. All numbers quoted below are copied from the CSV files in `outputs/` and `models/`.

Repo layout:

```
generate_data.py          provided generator, committed as-is
src/shipment_prep.py      shared constants + clean_shipments() + build_features()
part_a_clean_eda.py       cleaning, modelling table, checks, delay evidence
part_b_regression.py      delivery-hours regression
part_c_classification.py  delay classifier, feature selection, tuning, threshold
part_d_segments.py        hub profile, K-Means segments, tier check
package_model.py          saves the final classifier + artefacts to models/
predict_delay.py          scores data/new_shipments.csv -> outputs/new_shipment_actions.csv
data/                     generator output + modelling_table.csv
models/                   delay_model.pkl, delay_threshold.csv, feature_order.csv, impute_values.csv
outputs/                  every CSV named in the brief
```

## How to run

From a fresh clone, in this order (all commands from the repo root):

```bash
pip install -r requirements.txt
python generate_data.py          # prints: 24 1224 48
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

`requirements.txt` pins the exact versions I used (pandas, numpy, scikit-learn, joblib with `==`).

`models/delay_model.pkl` is regenerated by `python package_model.py`. The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt`; if your installed versions differ, re-run `package_model.py` instead of loading the committed pickle (the grader does the same). `package_model.py` also writes `outputs/part_d_reload_check.csv` which confirms the reloaded pickle gives the same probabilities as the in-memory model (`reload_max_abs_probability_diff = 0.0` on 180 test rows).

Running `predict_delay.py` twice gives byte-identical output.

## Data findings (Part A)

The raw export had 1,224 rows. After dropping 24 exact duplicates, 1,200 unique shipments remain, and all 1,200 survive the left merge with `hubs.csv` (`rows_after_hub_merge = 1200`). Before filling, there were 36 missing `distance_km`, 24 missing `parcel_weight_kg` (plus 5 sentinel rows with weight 999 that were treated as missing), 12 missing `declared_value` and 18 missing `payment_mode`. `service_type` had 12 spellings before strip + title-case and 3 after. Medians used for filling: distance 314.95 km, weight 1.83 kg, declared value INR 1,121.50. After cleaning there are 0 nulls across the 17 features and the two target columns. 278 of 1,200 parcels are delayed, a delay rate of 0.2317.

Findings (from `outputs/part_a_delay_by_group.csv` and `outputs/part_a_correlations.csv`):

1. **Express is delayed most often.** 119 of 243 Express parcels missed the 36 h promise, a delay rate of 0.4897. Standard is 0.2056 (132 / 642) and Economy only 0.0857 (27 / 315). Express has the tightest promise, so the same few hours of slack push it over the line.

2. **Delay rate climbs steeply with hub tier.** Tier 1: 0.0400 (16 / 400), Tier 2: 0.2150 (86 / 400), Tier 3: 0.4400 (176 / 400). Mean delivery hours go 48.57 -> 58.82 -> 63.49.

3. **Distance is the strongest single driver.** Delay rate by distance band: 0-200 km 0.0219, 201-400 km 0.1368, 401-600 km 0.4364, 601+ km 0.8523. Above 600 km, 75 of 88 parcels were late.

4. **Columns most correlated with `delivery_hours`** (ranked by absolute correlation, `delivery_hours` itself excluded): `promised_hours` 0.8372, `distance_km` 0.4013, `n_stops` 0.3247. The next two are `hub_daily_capacity` -0.3237 and `hub_tier` 0.3175. `promised_hours` dominates simply because the service type sets the base hours; distance and stops are the real operational signals. For the delay flag, `corr(is_delayed, distance_km) = 0.5455`.

5. **Why `declared_value_inr` was log-transformed.** On the filled column the mean is INR 1,533.05 but the median is INR 1,121.50, so the distribution has a long right tail. After taking the natural log the mean is 7.0277 and the median 7.0224, i.e. nearly symmetric, which is what the linear and distance-based models prefer.

Also from the checks file: `delivery_hours` has Q1 = 43.255, Q3 = 72.5625, so the 1.5 x IQR fences are -0.7063 and 116.5238; only 1 parcel is outside them. I kept it, there is no reason to drop a genuine slow delivery.

## Model results (regression, Part B)

Split: 840 / 180 / 180 (train / val / test) with `random_state=42`. The scaler was fitted on the 840 training rows only: `train_scaled_max_abs_mean = 0.0`, `test_scaled_max_abs_mean = 0.2187`, so the test rows clearly were not used to fit it.

**Baseline.** Predicting the training mean for every validation parcel gives R2 = -0.0212 (RMSE 18.8552 h). An R2 around zero means the baseline explains none of the variance; slightly negative because the validation mean differs a little from the training mean. Anything useful has to beat this.

**Candidates on validation** (`outputs/part_b_metrics.csv`):

| model | MAE | RMSE (h) | R2 |
|---|---|---|---|
| mean_baseline | 15.7952 | 18.8552 | -0.0212 |
| linear_regression | 3.9222 | 4.8912 | 0.9313 |
| decision_tree (depth 6) | 5.0971 | 6.2796 | 0.8867 |
| random_forest | 4.2541 | 5.4784 | 0.9138 |
| gradient_boosting | 3.9166 | 4.9165 | 0.9306 |

Linear regression won on validation RMSE (4.8912 h), with gradient boosting almost tied (4.9165 h). That makes sense given how the data was generated: the target is mostly a linear sum of the inputs plus a couple of interaction terms.

**Tree depth / bias-variance** (`outputs/part_b_tree_depth.csv`): depth 1 has train RMSE 11.6334 and val RMSE 12.1324, a gap of only 0.50 but both errors are high, so depths 1-3 are high-bias (underfitting). The best depth is 6 (val RMSE 6.2796; depth 1 is 5.85 h worse). From depth 8 onwards train RMSE keeps falling (3.336, 1.3613, 0.0 for unlimited) while val RMSE rises again (6.8385, 7.4173, 7.789), so depth 8, 12 and unlimited are high-variance (overfitting). The unlimited tree memorises the training set (train RMSE 0.0) and has a train/val gap of 7.79 h.

**Learning rate** (`outputs/part_b_gb_learning_rate.csv`): lr 0.01 -> R2 0.7127, lr 0.1 -> 0.9306, lr 1.0 -> 0.844. 0.1 is best. With 0.01 and only 100 trees the model has not moved far enough from the initial prediction yet (too slow, underfits). With 1.0 each tree over-corrects the previous one and the fit overshoots and becomes noisy.

**Cross-validation** (`outputs/part_b_cv.csv`, same `KFold(5, shuffle=True, random_state=42)` for both, 1,020 train+val rows): linear_regression mean R2 0.9261 (std 0.0048), gradient_boosting 0.9352 (std 0.0044). So CV ranks gradient boosting slightly ahead, while the single validation split ranks linear regression ahead. The difference is within one std either way. Following the rule in the brief, the final model is the validation winner, linear regression, and it scored R2 = 0.9493 (RMSE 4.5235 h, MAE 3.5671 h) on the 180 test rows, evaluated once.

If I had to ship one for planners I would still go with linear regression: the CV gap of 0.009 R2 is small, it is much faster to train and score, and its coefficients are easy to explain to ops ("every 100 km adds about 3 hours"). Gradient boosting would be the choice if the extra 1 percent of variance mattered more than interpretability.

## Model results (classification, Part C)

Stratified split: 840 / 180 / 180 with 195 / 42 / 41 delayed parcels.

**Blind baseline.** Predicting "on time" for everyone gives accuracy 0.7667 (TN 138, FP 0, FN 42, TP 0) but precision, recall and F1 all 0. It never catches a single delayed parcel, so accuracy on its own is a useless yardstick here.

**Three classifiers at the 0.5 rule** (`outputs/part_c_models.csv`):

| model | accuracy | precision | recall | f1 |
|---|---|---|---|---|
| logistic_regression | 0.9056 | 0.7778 | 0.8333 | 0.8046 |
| decision_tree_depth_6 | 0.8833 | 0.7561 | 0.7381 | 0.7470 |
| random_forest_default | 0.9111 | 0.8421 | 0.7619 | 0.8000 |

All three clearly beat the blind baseline. Depth 6 was the best tree depth by validation F1 among 2, 3, 4, 5, 6, 8, 10.

**Which columns carry signal** (`outputs/part_c_feature_scores.csv`). The top 7 by F-score are `distance_km` (389.21), `hub_tier` (155.35), `hub_daily_capacity` (144.13), `n_stops` (125.48), `promised_hours` (84.42), `rain_flag` (53.03) and `sale_event_flag` (36.73). All five bookkeeping columns rank 8 or lower with F-scores under 5 (`label_print_batch` 4.58 is the highest). Yet the default forest on all 17 columns gives those five noise columns a combined importance of 0.2253 — more than a fifth of its splits are spent on columns with no signal. That is the argument for dropping them.

**SelectKBest** (`outputs/part_c_selectk.csv`): k = 5 -> F1 0.6988, k = 7 -> 0.8333, k = 10 -> 0.8140, k = 12 -> 0.8049, k = 17 -> 0.8000. Five columns is too few (rain and sale flags are lost); seven is the peak; adding more only adds noise. k = 7 is used from here on.

**Tuning** (`outputs/part_c_tuning.csv`, selector fitted on training rows only):

| search | candidates | fits | best params | best cv accuracy | val F1 |
|---|---|---|---|---|---|
| grid_search | 27 | 135 | depth 6, leaf 1, 100 trees | 0.8952 | 0.7750 |
| randomized_search | 9 | 45 | depth 6, leaf 1, 50 trees | 0.8905 | 0.7901 |
| default_forest_same_7_features | 1 | 1 | no depth limit, leaf 1, 100 trees | - | 0.8333 |

Neither search beat the untuned forest on validation F1. Both searches optimise CV accuracy on 840 rows (where a depth limit looks marginally better), but on the 180-row validation set with 42 positives, one or two parcels move F1 by 0.02-0.03, so differences of this size are noise rather than evidence. The honest reading is that on a dataset this small, tuning the forest is not worth much once the noise columns are gone. Per the tie-break rule the final configuration is the default forest on the 7 selected columns (`outputs/part_c_final_config.csv`: k = 7, 100 trees, max_depth unlimited, min_samples_leaf 1).

**Alert threshold** (`outputs/part_c_thresholds.csv`). Ops rule: a missed delayed parcel costs more than an unnecessary call, so pick the highest threshold with validation recall >= 0.80.

| threshold | precision | recall | f1 |
|---|---|---|---|
| 0.3 | 0.6964 | 0.9286 | 0.7959 |
| 0.4 | 0.7400 | 0.8810 | 0.8043 |
| **0.5** | **0.7955** | **0.8333** | **0.8140** |
| 0.6 | 0.8889 | 0.7619 | 0.8205 |

0.6 has the best F1 but recall drops to 0.7619, under the floor. 0.5 is the highest threshold that still catches 35 of 42 delayed parcels (recall 0.8333) at precision 0.7955, i.e. 9 false alarms out of 44 calls. Going down to 0.4 would catch two more parcels at the cost of four more false alarms. Chosen threshold: **0.5**.

**One test evaluation** (`outputs/part_c_final_test.csv`): at threshold 0.5 on the 180 test rows, TN 125, FP 14, FN 10, TP 31; accuracy 0.8667, precision 0.6889, recall 0.7561, F1 0.7209. Test recall (0.7561) is lower than validation recall (0.8333). With only 41 delayed parcels in the test set, each missed parcel is 2.4 points of recall, so a drop of 3 parcels is within the noise of a set this size, but it also means the 0.80 recall target should be read as "roughly 3 in 4 to 4 in 5", not as a guarantee. Precision also fell (0.7955 -> 0.6889). The model was not re-tuned after seeing the test set.

## Operations recommendation (Part D)

**Hub segments.** The 24 hubs were profiled on mean delivery hours, delay rate, mean distance and mean stops, scaled, and clustered with K-Means (K = 3, `random_state=42`, `n_init=10`, hubs in ascending `hub_id` order). Clusters were named by their mean delay rate (`outputs/segment_profile.csv`):

| segment | hubs | mean hours | delay rate | mean km | mean stops |
|---|---|---|---|---|---|
| Standard | 7 | 47.24 | 0.0257 | 188.93 | 55.37 |
| Watch | 8 | 56.81 | 0.1550 | 314.18 | 70.72 |
| Escalate | 9 | 64.65 | 0.4600 | 470.48 | 84.34 |

**Escalate hubs and their delay rate** (from `outputs/hub_segments.csv` joined to `outputs/hub_profile.csv`): HUB19 Guwahati 0.62, HUB24 Agartala 0.54, HUB20 Raipur 0.48, HUB13 Nagpur 0.46, HUB17 Patna 0.46, HUB23 Siliguri 0.44, HUB21 Bhubaneswar 0.40, HUB18 Ranchi 0.38, HUB15 Kochi 0.36. Roughly every second parcel out of these nine hubs misses its promise. These are the hubs where a flagged parcel should go straight to the hub manager.

**Tier label vs actual behaviour** (`outputs/tier_vs_segment_mismatch.csv`): four hubs do not behave like their label.

- HUB07 Kolkata is Tier 1 but lands in Watch (delay rate 0.14, versus 0.02-0.04 for the other Tier 1 metros). It should not get the light-touch Tier 1 treatment.
- HUB13 Nagpur (Tier 2, delay rate 0.46) and HUB15 Kochi (Tier 2, 0.36) operate like Tier 3 hubs and belong in the Escalate playbook.
- HUB22 Dehradun is Tier 3 but behaves like a Tier 2 (Watch, delay rate 0.20); escalating every flagged parcel there would waste manager time.

Recommendation: use the segment, not the tier, to pick the playbook, and review the tier labels of these four hubs.

**Why K = 3.** `outputs/part_d_separation.csv` gives across/within distance ratios of 2.894 (K = 2, sizes 15-9), 5.3928 (K = 3, 9-8-7), 6.3047 (K = 4, 8-7-5-4) and 6.8866 (K = 5, 8-7-4-3-2). The ratio keeps rising, but K = 4 and K = 5 only do so by splitting off clusters of 4, 3 and 2 hubs, which are too small to carry their own playbook. K = 3 is also what the business runs (three playbooks), and the 9-8-7 split was the same for every seed and hub order I tried. Note the jump from K = 2 to K = 3 (2.89 -> 5.39) is far bigger than any later step.

**Alert threshold in practice.** The threshold is 0.5. From `outputs/part_c_final_test.csv`: precision 0.6889, so of every 10 parcels we flag, about 7 are really going to be late and 3 calls are unnecessary; recall 0.7561, so of every 10 parcels that will be late we catch between 7 and 8 and miss 2 to 3.

**The 48 new parcels** (`outputs/new_shipment_actions.csv`): 8 of 48 were flagged (delay probability >= 0.5). 6 of those are at Escalate hubs (HUB17, HUB18, HUB20, HUB21 x2, HUB24) and get *Escalate to hub manager*; the other 2 (HUB09 Jaipur, HUB22 Dehradun, both Watch) get *Proactive customer call*; the remaining 40 need no action.

## Production plan

**(a) Production-readiness characteristics mapped to this repo**

| characteristic | where it is in the repo |
|---|---|
| Accuracy | `outputs/part_c_final_test.csv` (one held-out test evaluation, F1 0.7209) and `outputs/part_b_metrics.csv` test row (R2 0.9493) |
| Reliability | `package_model.py` reloads the pickle and checks it against the in-memory model (`outputs/part_d_reload_check.csv`, diff 0.0); `predict_delay.py` fills gaps with stored medians so a missing field never crashes scoring |
| Reproducibility | every `random_state` fixed (42 everywhere, generator seeds 2604/7/99), `requirements.txt` pinned with `==`, `generate_data.py` committed verbatim, scripts run top to bottom from a clean clone |
| Consistency | training and prediction share the same `clean_shipments()` and `build_features()` from `src/shipment_prep.py`; column order is enforced by `models/feature_order.csv`; fill values come from `models/impute_values.csv` not recomputed on new data |
| Performance (speed) | final model is a 100-tree forest on 7 features; scoring 48 parcels in `predict_delay.py` is well under a second, and the regression winner is a linear model |
| Maintainability | constants (`FEATURES`, `NOISE_COLUMNS`, `PROMISED_HOURS`) live in one place; each Part is a separate script writing named CSVs, so a change in one Part can be re-run alone |
| Monitorability | every intermediate metric is a CSV in `outputs/`; the threshold is an external file (`models/delay_threshold.csv`) that ops can change without touching code |

**(b) What to monitor, with triggers**

1. *Weekly delayed share of delivered parcels.* Baseline is 0.2317. Trigger a review if a week falls outside 0.17-0.30 (roughly +/- 7 points); a sustained shift means the delay definition or the network has changed.
2. *Weekly share of parcels flagged.* On the 48 new parcels it was 8 / 48 = 0.167; on the test split 45 / 180 = 0.25. Trigger if the weekly flagged share is below 0.10 or above 0.35 — too few means the model has gone quiet, too many means the call queue will overflow.
3. *Recall on parcels whose outcome is now known* (flag at dispatch, compare once delivered, rolling 4 weeks). Test recall was 0.7561. Trigger retraining if rolling recall drops below 0.65.
4. *Precision on the same parcels.* Test precision 0.6889. Trigger if it drops below 0.55 (more than 4-5 wasted calls in 10).
5. *Input drift.* Mean `distance_km` per hub against `outputs/hub_profile.csv`; trigger if any hub moves more than 20 percent, since distance is the strongest feature.

**(c) Retraining schedule and the sale window**

- Retrain monthly on a rolling 6-month window, and immediately if a recall or precision trigger fires. Re-run `part_d_segments.py` quarterly; if a hub changes segment, the playbook assignment changes with it.
- The 15-28 September sale window is a different regime: `sale_event_flag` adds about 7 hours (12 more for Express) in the generator, and the real data will behave the same way. Do not compare sale weeks against ordinary weeks when checking the triggers above; compare them against the previous sale window, and make sure the training window always contains at least one full sale period so the flag has examples to learn from. If a new sale is announced on different dates, the flag logic in the feature pipeline has to be updated before the sale, not after.
- Data drift here would look like: the hub profile changing (a Tier 2 hub starting to look like Escalate), the share of long lanes (> 600 km) rising, a new service type or payment mode appearing that `clean_shipments()` does not know, or the distribution of `delay_probability` shifting so that the 0.5 threshold flags far more or far fewer parcels than before. Any of these should trigger a re-run of Parts A to D and a fresh look at the threshold table.

## Limitations

1. **Synthetic data.** Every row comes from `generate_data.py`. The relationships are clean and mostly linear, which is why linear regression reaches R2 0.93. Real Delhivery data will have rider behaviour, address quality and weather that are not in these 17 columns; the exact numbers here will not carry over, only the pipeline will.
2. **Small positive class.** The test set has only 41 delayed parcels and validation 42. One parcel is about 2.4 points of recall, so the test recall of 0.7561 vs validation 0.8333 is not a reliable sign of anything. Confidence intervals on all the classification metrics are wide.
3. **Threshold tuned on one validation split.** The 0.5 threshold came from a single 180-row split. A different seed could easily have picked 0.4 or 0.6. In production the threshold should be re-estimated on a few months of real outcomes.
4. **Tuning results are not conclusive.** Grid and randomized search did not beat the default forest, but with 840 training rows that says more about the sample size than about the hyper-parameters.
5. **Hub segments use 50 parcels per hub.** A hub delay rate of 0.46 from 50 parcels has a standard error of about 0.07, so neighbouring hubs (e.g. Ranchi 0.38 and Kochi 0.36) are not really distinguishable. The four tier mismatches are the clear cases; borderline hubs should be re-checked with more data.
6. **No cost model.** "A missed delayed parcel costs more than an unnecessary call" was turned into a recall >= 0.80 rule because no actual rupee costs were given. With real costs the threshold should be chosen by minimising expected cost instead.
